# TODO API

Список замечаний и задач по доработке API Raspberry Pi Router.

## Критичные задачи

### 1. Защита API

Сейчас Flask API слушает:

`0.0.0.0:8080`

При этом в API отсутствует аутентификация.

Необходимо:

* добавить механизм авторизации;
* для первой версии рассмотреть простой API-токен;
* запретить выполнение управляющих запросов без авторизации;
* отдельно проверить доступность порта `8080` из Wi-Fi/LAN сети;
* учитывать дальнейший удалённый доступ через VPS.

Особенно критичны запросы:

* изменение `access_mode`;
* создание/удаление пользователей;
* создание/удаление устройств;
* изменение расписания.

---

### 2. Исправить удаление заблокированного устройства

Сейчас `DELETE /devices/<device_id>` удаляет устройство только из SQLite.

Проблема:

если MAC устройства в момент удаления находится в nftables set `blocked_macs`, после удаления записи из таблицы `devices` `schedule_engine.py` больше не будет обрабатывать этот MAC.

В результате MAC может навсегда остаться в `blocked_macs`.

Необходимо:

* перед удалением устройства проверить наличие его MAC в `blocked_macs`;
* при наличии удалить MAC из `blocked_macs`;
* только после успешного удаления из firewall удалить устройство из БД;
* определить поведение при ошибке nftables.

---

### 3. Добавить API фактического состояния устройства

Сейчас:

`GET /access/<user_id>`

показывает вычисленное состояние доступа пользователя.

Но API не предоставляет фактическое состояние конкретного устройства, применённое `schedule_engine.py`.

Необходимо предоставить данные из `device_state` и/или nftables.

Возможные варианты:

`GET /device-state`

или добавить состояние в:

`GET /devices`

Желательные поля:

* `action`: `ALLOW` / `BLOCK`;
* `reason`;
* `timestamp`;
* фактическое наличие MAC в `blocked_macs`.

Windows-приложение должно иметь возможность отличать:

* что должно быть по расписанию;
* что фактически применено firewall.

---

### 4. Проверить скорость применения изменений access_mode

Сейчас:

`PATCH /users/<user_id>/access_mode`

изменяет только SQLite.

Фактическое изменение nftables выполняет отдельный `schedule_engine.py`.

Необходимо:

* определить, как сейчас запускается `schedule_engine.py`;
* проверить systemd service/timer или cron;
* определить период его запуска;
* решить, должен ли API после изменения режима немедленно применять новое состояние;
* обеспечить предсказуемую задержку между нажатием кнопки в клиенте и фактической блокировкой/разблокировкой.

Для Windows-приложения предпочтительно, чтобы команды:

* «Всегда разрешать»;
* «Всегда блокировать»;
* «По расписанию»

применялись практически сразу.

---

## Архитектурные задачи

### 5. Убрать дублирование функции check_access

Сейчас логика определения доступа присутствует минимум в:

* `app.py`;
* `schedule_check.py`;
* `schedule_engine.py`.

Риск:

при изменении алгоритма расписания реализации могут начать отличаться.

Необходимо:

* вынести общую логику определения доступа в отдельный модуль, например `access_control.py`;
* использовать одну функцию во Flask API;
* использовать ту же функцию в `schedule_engine.py`;
* использовать её же в диагностических скриптах.

---

### 6. Привести инициализацию базы данных к единой схеме

Сейчас `database.py` создаёт:

* `users`;
* `devices`;
* `schedules`.

Дополнительно отдельными скриптами создаются/изменяются:

* `users.access_mode`;
* `access_log`;
* `device_state`.

Необходимо:

* определить актуальную окончательную схему БД;
* обеспечить создание новой БД из одного механизма;
* сохранить возможность обновления существующих БД;
* избежать ошибок повторного запуска миграций.

Текущие отдельные скрипты:

* `update_db.py`;
* `add_access_log.py`;
* `add_device_state.py`.

В дальнейшем желательно ввести систему версий/миграций БД.

## Проверка и нормализация данных

### 7. Улучшить проверку имени пользователя

`POST /users` сейчас проверяет наличие поля `name`, но недостаточно строго проверяет содержимое.

Необходимо использовать такую же проверку, как при `PATCH /users/<id>`:

* значение должно быть строкой;
* после `strip()` строка не должна быть пустой;
* в БД сохранять нормализованное значение.

---

### 8. Нормализовать MAC-адреса

Сейчас MAC может поступать в API в разном регистре.

В `schedule_engine.py` MAC дополнительно переводится в lowercase.

Необходимо:

* нормализовать MAC при добавлении устройства;
* желательно всегда хранить MAC в lowercase;
* проверить формат MAC;
* при необходимости нормализовать MAC при сравнении и обновлении.

Пример канонического вида:

`ca:ef:d8:95:11:b5`

---

### 9. Проверить изменение имени устройства и пользователя в device_state

`device_state` обновляется при изменении:

* `action`;
* `reason`.

При обычном переименовании устройства или пользователя информация в `device_state` может остаться старой до следующего изменения состояния.

Необходимо:

* либо обновлять `device_state` при переименовании;
* либо не хранить `device_name` и `user_name` как копии;
* либо получать актуальные имена через JOIN при выдаче API.

---

## API для Windows-приложения

### 10. Зафиксировать назначение /clients и /devices

Текущее разделение сохранить:

`GET /clients`

обнаруженные DHCP/Wi-Fi клиенты.

`GET /devices`

устройства, зарегистрированные в системе управления доступом.

Предполагаемое использование Windows-приложением:

**Обнаруженные устройства**

* IP;
* MAC;
* DHCP hostname;
* online;
* зарегистрировано/не зарегистрировано.

**Управляемые устройства**

* ID;
* MAC;
* имя;
* пользователь;
* состояние доступа.

---

### 11. Зафиксировать формат weekday

Текущий API использует ISO-нумерацию:

* `1` — понедельник;
* `2` — вторник;
* `3` — среда;
* `4` — четверг;
* `5` — пятница;
* `6` — суббота;
* `7` — воскресенье.

Windows-клиент должен использовать ту же нумерацию.

Не переходить незаметно на `0–6`.

---

### 12. Зафиксировать значения access_mode

Допустимые значения:

`schedule`

`always_allow`

`always_block`

Windows-клиент должен считать именно эти строковые значения частью API-контракта.

Отображение в GUI:

* `schedule` → «По расписанию»;
* `always_allow` → «Всегда разрешать»;
* `always_block` → «Всегда блокировать».

---

### 13. Не дублировать расчёт расписания в Windows-клиенте

Windows-приложение не должно самостоятельно решать, разрешён Интернет или нет.

Источник истины:

**Raspberry Pi API / schedule engine.**

Windows-клиент должен:

* изменять настройки;
* получать состояние;
* отображать результат.

Это позволит избежать различий между логикой Windows-приложения и Raspberry Pi.

## Логи

### 14. Определить назначение двух журналов

Сейчас присутствуют:

`/var/log/rpi-router/access.log`

и таблица:

`access_log`

Файловый журнал записывает работу `schedule_engine.py`.

Таблица `access_log` хранит изменения состояния ALLOW/BLOCK и используется endpoint:

`GET /logs`

Необходимо сохранить это различие или явно его документировать.

---

### 15. Расширить GET /logs при необходимости

Сейчас `/logs` возвращает последние 50 записей.

В будущем для Windows-приложения рассмотреть:

* параметр `limit`;
* фильтр по пользователю;
* фильтр по устройству;
* фильтр по времени;
* постраничную выдачу.

Не является обязательным для первой версии.

`/api/v1/users`

или возвращать версию через `/status`.

Это позволит в будущем изменять API без поломки старых клиентов.

# Текущий статус

API уже поддерживает основные операции, необходимые Windows-приложению:

* управление пользователями;
* управление устройствами;
* назначение устройств пользователям;
* управление расписаниями;
* ручное разрешение доступа;
* ручную блокировку;
* работу по расписанию;
* обнаружение Wi-Fi/DHCP клиентов;
* получение журнала переключений.

Основную архитектуру API менять не требуется. Рекомендуется выполнить перечисленные исправления эволюционно, сохранив существующие endpoint'ы и совместимость с будущим Windows-клиентом.
